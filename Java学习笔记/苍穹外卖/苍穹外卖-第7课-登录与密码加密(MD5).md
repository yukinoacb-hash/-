# 苍穹外卖 · 第 7 课：登录与密码加密（MD5）

## 📖 知识点概述（一句话）

登录 = **前端传来用户名和密码 → 后端查库 → 比对密码 → 发一张"通行证"（JWT）**。
但在写登录之前，必须先解决一个前提：**数据库里绝不能存明文密码**。

---

## 🧠 一、为什么密码不能明文存？

### ❌ 错误做法
```
数据库 employee 表
username    password
admin       123456        ← 明文，谁拿到库谁就知道密码
```

**后果**：数据库一旦泄露（被拖库、被内鬼导出、备份文件丢失），
**所有用户的密码直接暴露**。更可怕的是 —— 很多人所有网站用同一个密码，
你泄露一次，等于害了用户的银行、邮箱、微信。

### ✅ 正确做法：存"摘要"

```
用户输入：123456
     ↓  MD5
数据库存：e10adc3949ba59abbe56e057f20f883e
```

---

## 🧠 二、MD5 是什么？

### 一句话：把任意长度的内容 → 变成固定长度的一串字符

```
"123456"      → e10adc3949ba59abbe56e057f20f883e   (32 位十六进制)
"123457"      → 14e1b600b1fd579f47433b88e8d85291
"一整个文件"   → XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX   (还是 32 位)
```

### 三个关键特点

| 特点 | 含义 |
|---|---|
| **固定长度** | 不管输入多长，输出永远 32 位十六进制 |
| **不可逆** | **推不回去**！拿到摘要算不出原文 |
| **一点点不同就全变** | 输入差一个字，输出完全不一样（叫"雪崩效应"） |

### ⚠️ 最重要的一点：MD5 不是"加密"

| | 加密（如 AES） | 摘要（如 MD5） |
|---|---|---|
| 能不能还原 | **能**（有密钥就能解密） | **永远不能** |
| 用途 | 传输数据、存敏感信息 | **存密码**、校验文件完整性 |

**为什么存密码要用"不可逆"的？**
因为"能不能还原"本身就是风险 —— 加密就会**有密钥**，服务器被攻破了密钥也在服务器上，
等于白干。而摘要**根本没有密钥**，**连你自己都不知道用户的原密码**（所以忘记密码只能"重置"，不能"找回"）。

### 那既然不可逆，怎么验证密码对不对？

**再算一遍比对**：

```
用户登录输入 "123456"
      ↓ MD5
   e10adc39...
                ⟺  跟数据库里存的比一比 → 一样就通过
```

**全程不需要知道原密码，只需要比对摘要。**

## 🧠 三、彩虹表 与 加盐（进阶，了解一下）

### 彩虹表攻击
"123456" 这种常见密码，MD5 值早就被人算好做成表了：

```
e10adc3949ba59abbe56e057f20f883e = 123456    ← 一查就知道
```

所以**光 MD5 也不够安全**。

### 加盐（Salt）
给每个密码**额外拼一截随机字符串**再算 MD5：

```
"123456" + 随机盐"a8F2x" → 算 MD5 → 得到一个全世界独一无二的值
```

- 盐**每个用户不同**，所以两个人密码相同，**存进去的值也不一样**
- 彩虹表直接失效（因为没人预计算过 "123456a8F2x"）

### 现实中的选择（记住这个结论就行）

| 方案 | 安全性 | 说明 |
|---|---|---|
| 明文 | 💀 零分 | 绝对不许 |
| MD5 | ⭐ 及格线 | 学习用；**苍穹外卖项目用的就是它** |
| MD5 + 盐 | ⭐⭐ | 好一些，但要自己管理盐 |
| **BCrypt** | ⭐⭐⭐⭐ | **真实项目的推荐做法**，自带盐、可调计算强度（Spring Security 里有） |

> 本课按苍穹外卖的写法用 **MD5**，先把整个登录链路跑通；
> 以后做真实项目时换 BCrypt（概念一样，只是换了个工具方法）。

## 📝 四、代码：用 Spring 自带的工具算 MD5

**不用自己写算法**，Spring 里就有（`spring-core`，你项目已经依赖了）：

```java
import org.springframework.util.DigestUtils;

String md5 = DigestUtils.md5DigestAsHex("123456".getBytes());
// → e10adc3949ba59abbe56e057f20f883e
```

| 方法 | 返回 | 说明 |
|---|---|---|
| `DigestUtils.md5DigestAsHex(byte[])` | 32 位十六进制**字符串** | 存数据库用这个 |
| `DigestUtils.md5Digest(byte[])` | 16 字节的 `byte[]` | 一般不用 |

> `getBytes()` 是把字符串转成字节数组 —— MD5 算法处理的是**字节**，不是字符。
> （`getBytes()` 不传参用平台默认编码，规范写法是 `getBytes(StandardCharsets.UTF_8)`）

### 🔴 放在哪一层加密？

**Service 层**，而且是在**调 Mapper 之前**：

```java
// EmployeeServiceImpl
@Override
public int insert(Employee employee){
    employee.setPassword(DigestUtils.md5DigestAsHex(employee.getPassword().getBytes()));  // ← 先加密
    employee.setStatus(1);
    employee.setCreateTime(LocalDateTime.now());
    employee.setUpdateTime(LocalDateTime.now());
    return employeeMapper.insert(employee);
}
```

**为什么不在 Controller？** 业务规则（密码怎么存）属于业务层；Controller 只管收请求。
**为什么不在 Mapper？** Mapper 只管 SQL，不做逻辑。

## ⚠️ 注意事项 / 常见坑

### 坑 1：别忘了把数据库里的历史密码也改掉
只改代码不行 —— **已经存进库的明文密码还是明文的**。
要把现有数据的 `password` 一起更新成 MD5 值：

```sql
UPDATE employee SET password = 'e10adc3949ba59abbe56e057f20f883e'
WHERE username = 'admin';
```
（`e10adc3949ba59abbe56e057f20f883e` 就是 `123456` 的 MD5）

### 坑 2：`getBytes()` 要看清楚传进去的是什么
`DigestUtils.md5DigestAsHex(employee.getPassword().getBytes())` ——
如果 `getPassword()` 是 `null`，这里直接**空指针**。后面登录接口要做非空校验。

### 坑 3：登录时比对密码，也要先加密再比
```java
String md5 = DigestUtils.md5DigestAsHex(password.getBytes());
if (!md5.equals(employee.getPassword())) { ...失败... }
```
**永远不要**反过来"把库里的密码解密" —— 解不了，也不需要。

### 坑 4：字符串比较用 `equals`，不要用 `==`
`String` 的 `==` 比的是"是不是同一个对象"，`equals` 比的才是"内容是否相同"。

```

```

前端传的是明文 `888888`，进库变成了 32 位密文 —— 说明 `EmployeeServiceImpl.insert()`
里的 `DigestUtils.md5DigestAsHex(...)` 确实生效了。

> | id | username | password（都是密文） | 明文 |
> |---|---|---|---|

### 3. 顺带说明：为什么"改一行代码"必须重启
Spring Boot 启动时会把 `target/classes` 里编译好的 `.class` 载入内存，
你在 IDEA 里改的是 `.java` 源码。**不重新编译 + 重启，跑的还是老代码。**
## 🕳️ 坑 5：同一个 username 连续 POST 两次 → 500（不是代码坏了）

**现象**：验证 lisi 加密时，第一次 POST 返回 200，又点了一次运行 → 500。

**排查过程（笔记版）**：

1. 查库 —— `lisi` **已经在库里了**（id=10，密码是 MD5）→ 说明插入本身是成功的
2. 看 `.idea/httpRequests/http-requests-log.http` —— 历史记录里躺着两条：
   - `21:21:44` 的 POST → **200**（`2026-10-05T212144-3.200.json`）
   - `21:21:48` 的 POST → **500**（`2026-10-05T212148.500.json`）
3. 结论：**两次请求、同一个用户名** → 撞上 `username` 的 UNIQUE 唯一索引

**真正的报错**（在 IDEA 下面的 Run 控制台里找 `Caused by:`）：

```
Caused by: java.sql.SQLIntegrityConstraintViolationException:
Duplicate entry 'lisi' for key 'employee.username'
```

### 复习：怎么读 Java 的异常堆栈

```
Error starting / 500 Internal Server Error     ← 最上面：Spring 包装后的"表面现象"
  ...
Caused by: xxx                                  ← 中间：一层层往下扒
  ...
Caused by: java.sql.SQLIntegrityConstraintViolationException: Duplicate entry ... ← 最底下：真正的根因
```

> **口诀：别看最上面，看最下面的 `Caused by`。**
> 浏览器只给你一句 `500 Internal Server Error`，
> 真正有用的信息**只在 IDEA 的控制台里** —— 这就是"看日志"的能力。

### 这件事的正确处理方式（以后要学）

给用户看 500（服务器内部错误）是**不对的**，用户看不懂。真实项目要返回人话：

- 苍穹外卖原项目做法：Service 里先 `employeeMapper.getByUsername(username)` 查一下，
  存在就抛自定义异常 `DuplicateEntryException`（继承 `BaseException`）
- 再写一个全局异常处理器 `GlobalExceptionHandler`（`@RestControllerAdvice`）
  统一把它翻译成 `Result.error("xxx已存在")` 返回给前端

> 这部分等员工模块收尾、进异常处理专题时补上。

## 📖 知识点概述

### 为什么先做分类

菜品必须属于某个分类：

- "宫保鸡丁" 属于 **川菜**（菜品分类 type=1）
- "商务套餐A" 属于 **套餐分类**（type=2）

**分类是菜品的爹。没有分类，菜品没法建。**

所以顺序是：**分类 → 菜品 → 套餐**。

### 三、category 表结构

```sql
CREATE TABLE category (
    id          BIGINT       PRIMARY KEY AUTO_INCREMENT COMMENT '主键',
    type        INT          COMMENT '分类类型：1菜品分类 2套餐分类',
    name        VARCHAR(32)  NOT NULL UNIQUE COMMENT '分类名称',
    sort        INT          NOT NULL DEFAULT 0 COMMENT '排序',
    status      INT          COMMENT '状态：0禁用 1启用',
    create_time DATETIME     COMMENT '创建时间',
    update_time DATETIME     COMMENT '修改时间',
    create_user BIGINT       COMMENT '创建人id',
    update_user BIGINT       COMMENT '修改人id'
) COMMENT '分类表';
```

| 列 | 为什么这么设计 |
|---|---|
| `id` | 主键，和 employee 一样自增 |
| **`type`** | 1 = **菜品分类**（川菜/粤菜/饮品），2 = **套餐分类**（商务套餐/儿童套餐）。前端两个下拉框分开显示，靠这个字段区分 |
| `name` | `NOT NULL UNIQUE` → 不能空、不能重名（和 employee.username 一个道理） |
| `sort` | 排序号，前端按这个数字排。比如"热销"排第 1、"主食"排第 5 |
| `status` | 0 禁用 / 1 启用。禁用后用户端看不到 |
| `create_time` / `update_time` | 什么时候建的、什么时候改的 |
| **`create_user`** / **`update_user`** | ⭐ **谁建的、谁改的** ← BaseContext 的用武之地 |

### 四、🔑 BaseContext 终于要派上用场了

新增一个分类时，`create_user` 该填什么？**填"当前登录员工的 id"。** 那个 id 从哪来？

```java
BaseContext.getCurrentId()   // ← 拦截器验完 token 存进柜子的那个
```

**第 10 课写的东西，到这里开始真正干活。**

### 五、为什么会有"公共字段"这个概念

| 表 | create_time | create_user | update_time | update_user |
|---|---|---|---|---|
| `employee` | ✅ | ❌（早期漏了） | ✅ | ❌ |
| `category` | ✅ | ✅ | ✅ | ✅ |

# 📌 写实体类时的类型对照表 + 4 个易错点（2026-10-12 补）

## 数据库类型 → Java 类型

| 数据库列类型 | Java 用 | 为什么 |
|---|---|---|
| `bigint` | `Long` | 装得下大数字（Integer 上限约 21 亿，会溢出） |
| `int` | `Integer` | 因为列允许 NULL，`int` 基本类型装不下"空" |
| `varchar` | `String` | — |
| `datetime` | `LocalDateTime` | — |

⭐ **核心口诀**：**大数字用 Long，可能为空用包装类。**

## 列名 → 属性名：靠驼峰自动映射

数据库 `create_time` ↔ Java `createTime`，靠的是 yml 里：

```yaml
mybatis:
  configuration:
    map-underscore-to-camel-case: true
```

⚠️ Java 里必须写驼峰 `createTime`。写成 `create_time` 就永远取不到值（一直 null）。

## category 表 → Category.java 的 9 个字段

```java
private Long id;              // bigint 主键
private Integer type;         // int  1菜品分类 2套餐分类
private String name;          // varchar(32)
private Integer sort;         // int  排序
private Integer status;       // int  0禁用 1启用
private LocalDateTime createTime;   // datetime
private LocalDateTime updateTime;   // datetime
private Long createUser;      // bigint 创建人id ★
private Long updateUser;      // bigint 修改人id ★
```

## ⚠️ 实写时踩到的 4 个坑（2026-10-12）

| # | 写成了 | 应该是 | 为什么 |
|---|---|---|---|
| 1 | `public class createTime` | `public class Category` | **public 类名必须和文件名一致**，否则编译不过；而且 Mapper/Controller 都要用 `Category` 这个名字 |
| 2 | 没写 `@Data` | 加 `@Data` + `import lombok.Data;` | 没有它 Lombok 不生成 getter/setter，`category.getName()` 直接编译不过 |
| 3 | `private Integer id` | `private Long id` | 数据库是 `bigint`，Integer 会溢出 |
| 4 | 漏了 `createUser` | 补 `private Long createUser;` | 表里有 `create_user` / `update_user` **两列**，容易只写一半 |

## ⭐ 记忆法

一个实体类 = **"一张表的 Java 分身"**：
- 表有 9 列 → 类有 9 个字段（不多不少）
- 每列的类型按对照表翻译
- 类名 = 表名首字母大写（`category` → `Category`）
- 只装数据，**不写业务逻辑**

# 🗂️ 第 2 步：CategoryMapper 接口（2026-10-12）

## Mapper 接口是什么

一句话：**Mapper 接口 = 一张"我要执行哪些 SQL"的清单。**

三件事：

| 要素 | 说明 |
|---|---|
| `@Mapper` | 告诉 MyBatis"这是个 Mapper"，启动时扫描它生成实现类 |
| 方法声明 | 每个方法 = 一条 SQL 的名字 |
| SQL 从哪来 | 简单 SQL 用注解（`@Select`/`@Insert`/`@Delete`），动态 SQL 放 XML |

⚠️ 接口**没有实现类**。你在 `EmployeeServiceImpl` 里能 `@Autowired EmployeeMapper`，是因为 **MyBatis 在启动时动态生成了实现类**。

## 分类管理需要的 6 个方法

| 方法 | 服务于哪个接口 | SQL 写在哪 |
|---|---|---|
| `int insert(Category category)` | 第 3 步 新增分类 | 注解 `@Insert` |
| `Category getByName(String name)` | 第 3 步 新增前查重名 | 注解 `@Select` |
| `Category getById(Long id)` | 第 6 步 修改前回显 | 注解 `@Select` |
| `int deleteById(Long id)` | 第 7 步 删除分类 | 注解 `@Delete` |
| `int update(Category category)` | 第 5、6 步 启停 / 修改 | ⏳ XML（第 6 步写，复用动态 SQL） |
| `List<Category> list(Category category)` | 第 4 步 分页查询 | ⏳ XML（第 4 步写） |

## ⭐ 为什么需要 `getByName`

因为建表时给 `name` 加了**唯一索引**：

```sql
UNIQUE KEY `name` (`name`)
```

新增一个重名的分类，MySQL 会直接抛：

```
Duplicate entry 'xxx' for key 'category.name'
```

→ 前端看到的是 **500 + 一坨英文堆栈**。

**正确做法**：在 Service 里**先查一遍**，查到了就返回友好提示「分类名称已存在」，而不是等数据库报错。

（这就是员工那边踩过的坑：`Duplicate entry 'lisi' for key 'employee.username'` → 500。同一个问题。）

## ⚠️ 写 insert 时的两个注意点

1. **`id` 是自增的，insert 的列里不能写 `id`** —— 让数据库自己生成
2. 除了 `id`，其余 **8 列都要列出来**并对应 `#{}`

```sql
INSERT INTO category (type, name, sort, status, create_time, update_time, create_user, update_user)
VALUES (#{type}, #{name}, #{sort}, #{status}, #{createTime}, #{updateTime}, #{createUser}, #{updateUser})
```

## ⚠️ 为什么 `createUser` / `updateUser` 现在不用担心值

第 3 步写新增接口时才会处理 —— 到时候从 `BaseContext.getCurrentId()` 取。
**BaseContext 真正派上用场的地方，就在这里。**

# 🐞 第 2 步实写踩坑（2026-10-12）

## 三处错，五个点

### ① 多余 import

```java
import com.sky.skytakeout.entity.Employee;   // ← 用不到，删掉
```

写哪个 Mapper 就只 import 哪个实体。

### ② `@Select` 里的 SELECT 顺序写反了

```java
@Select("SELECT FROM category WHERE name=#{name}")   // ❌ 少了 *
@Select("SELECT FROM * category WHERE id=#{id}")     // ❌ 位置反了
```

正确：

```java
@Select("SELECT * FROM category WHERE name=#{name}")  // ✅
@Select("SELECT * FROM category WHERE id=#{id}")      // ✅
```

⭐ **SQL 骨架口诀**：`SELECT 列 FROM 表 WHERE 条件` —— **顺序是死的**。

### ③ 返回值类型错了

```java
int getByName(String name);    // ❌
int getById(Long id);          // ❌
```

应该是 `Category`。

⭐ **怎么判断返回类型**：看**查询结果的形状**

| 查出来是什么 | 返回类型 |
|---|---|
| 一整行数据（多个列） | **实体类**（`Category`） |
| 一个数字（如 `COUNT(*)`） | `int` / `Integer` |
| 多行数据 | `List<实体类>` |
| 改了几行（增删改） | `int` |

## ⚠️ 最大的教训：SQL 是写在字符串里的，编译器管不了

这两处 SQL 错误，**IDEA 一点都不会报** —— 编译全绿，直到运行时才炸：

```
SQLSyntaxErrorException: You have an error in your SQL syntax
```

**护身符**：SQL 先丢到 Navicat 里跑通，**能出结果了再抄进 Java**。

## 关于 update / list 这两个"空方法"

现在它们只有方法声明、没有 SQL：

- ✅ 编译通过、启动也正常
- ❌ 但**一旦调用**就报 `Invalid bound statement (not found)`

所以它们暂时是"待办清单"——**第 4 步写 `list` 的 XML，第 6 步写 `update` 的 XML**，写到哪步才用哪步。

# 🔁 DTO → Entity 的"搬运"（2026-10-12 踩坑）

## 为什么非要有这一步

`CategoryDTO` 和 `Category` 是**两个不同的类**，字段不一样：

| 字段 | CategoryDTO | Category |
|---|---|---|
| type / name / sort | ✅ | ✅ |
| id | ❌ | ✅ |
| status | ❌ | ✅ |
| createTime / updateTime | ❌ | ✅ |
| createUser / updateUser | ❌ | ✅ |

所以 `categoryDTO.setStatus(1)` **编译不过** —— DTO 里没这个字段。
而 `categoryMapper.insert(categoryDTO)` 也编译不过 —— 它要的是 `Category`。

## ⭐ 搬运口诀：**目标.setX( 来源.getX() )**

把 DTO 想成"旧家"，Entity 想成"新家"：

```java
Category category = new Category();              // 新家（空的）
category.setName(categoryDTO.getName());         // 从旧家拿出来 → 放进新家
category.setType(categoryDTO.getType());
category.setSort(categoryDTO.getSort());
```

- **左边** `category.` = 新家（往哪放）
- **括号里** `categoryDTO.getX()` = 旧家（从哪拿）

## ❌ 写反了会怎样

```java
categoryDTO.setName(categoryDTO.getName());   // ❌ 从旧家拿出来，又放回旧家
```

等于**什么都没干**，`category` 永远是空的：

- `category.name` = null、`type` = null、`sort` = null
- INSERT 时 MySQL 直接拒绝：`Column 'name' cannot be null`（建表时 name 是 NOT NULL）
- 前端看到 **500**

**症状**：编译全绿、代码"看起来在搬"，但一提交就 500。

## 💡 以后有更省事的写法

```java
BeanUtils.copyProperties(categoryDTO, category);   // 一行搬完同名字段
```

（`org.springframework.beans.BeanUtils`）现在手写是为了知道它在搬什么。

## 📌 完整流程回顾

```java
// ① 查重名
Category exist = categoryMapper.getByName(categoryDTO.getName());
// ② 重名就撤
if (exist != null) { return 0; }
// ③ 搬运：DTO → Entity（目标.setX(来源.getX())）
Category category = new Category();
category.setType(categoryDTO.getType());
category.setName(categoryDTO.getName());
category.setSort(categoryDTO.getSort());
// ④ 补后端该填的 5 个字段
category.setStatus(1);
category.setCreateTime(LocalDateTime.now());
category.setUpdateTime(LocalDateTime.now());
Long empId = BaseContext.getCurrentId();   // ★ 拦截器存进来的
category.setCreateUser(empId);
category.setUpdateUser(empId);
// ⑤ 落库
return categoryMapper.insert(category);
```

## 🎯 追问：Controller 方法能不能写成 void？

### 一句话结论
**不要。** Controller 方法的返回类型 **就是 HTTP 响应体**。写 void = 响应体是空的，前端拿不到 `code` / `msg`。

### 三种写法对比

| Controller 写法 | 实际发给前端的响应体 | 前端能判断成功吗 |
|---|---|---|
| `public String insert(...)` | 纯文字 `添加成功` | ❌ 只能靠猜文字，中文还会乱码 |
| `public Result<Void> insert(...)` | `{"code":1,"msg":"操作成功","data":null}` | ✅ 看 code |
| `public void insert(...)` | **空**（HTTP 200，body 长度 0） | ❌ `res.data` 是空字符串，`.code` 是 undefined |
| `public Result<Employee> insert(...)` | `{"code":1,...,"data":{员工}}` | ✅ 但多送了数据 |

所以 void 不是"更简洁"，是"不返回任何结果"。

### 真正要选的，其实是 Result<T> 里的 T

| 接口类型 | 举例 | 泛型怎么写 |
|---|---|---|
| 查询 / 登录（要带数据回去） | findAll、findById、login | `Result<List<Employee>>`、`Result<Employee>`、`Result<EmployeeLoginVO>` |
| 新增 / 修改 / 删除（只要个成功信号） | insert、update、deleteById | `Result<Void>` + `return Result.success();` |

`Void` 就是"这个接口不带货"的占位符，和查询接口必带数据的区别。

### 目前项目里的实际情况（2026-10-12 检查）

| 方法 | 现在写的 | 建议 |
|---|---|---|
| findAll | `Result<List<Employee>>` + `success(list)` | ✅ 对 |
| findById | `Result<Employee>` + `success(employee)` | ✅ 对 |
| insert | `Result<Employee>` + `success(employee)` | 可改成 `Result<Void>` 统一风格 |
| deleteById | `Result<Void>` + `success()` | ✅ 对 |
| update | 声明 `Result<Employee>`，却 `return Result.success();` | ⚠️ 声明改成 `Result<Void>` |
| login | `Result<EmployeeLoginVO>` + `success(vo)` | ✅ 对 |

### ⚠️ 注意：update 那种写法为什么能编译过
```java
public Result<Employee> update(...) {
    return Result.success();          // 没传数据，却能编译
}
```
因为 `Result.success()` 是静态泛型方法 `<T> Result<T> success()`，**T 由左边声明的类型猜出来**（这里猜成 Employee），编译器就不报错。
但这是"声明说带 Employee、实际没带"，语义自相矛盾，容易让后面看代码的人误解 —— 所以建议把声明改成 `Result<Void>`，和 deleteById 保持一致。

### 📌 新增接口要不要把 employee 返回给前端？
- 一般不需要：前端表单提交后，只看 `code` 判断成功，成功就刷新列表（重新 GET 一次）。
- 唯一有用的场景：如果 insert 的 XML 写了 `useGeneratedKeys="true" keyProperty="id"`，此时 `employee.getId()` 是数据库刚生成的主键，返回给前端可以拿去做下一步跳转。
- 苍穹外卖的前端不需要，所以用 `Result<Void>` 就够。

### ✅ 规范版 EmployeeController —— 只动 2 处

改动原则：**查询/登录带数据，增删改不带数据（`Result<Void>`）**。

| 位置 | 原来 | 改成 |
|---|---|---|
| `insert` 返回类型 | `Result<Employee>` | `Result<Void>` |
| `insert` 成功那行 | `return Result.success(employee);` | `return Result.success();` |
| `update` 返回类型 | `Result<Employee>` | `Result<Void>` |

其余 4 个方法（findAll / findById / deleteById / login）本来就是对的，不动。

```java
@PostMapping
public Result<Void> insert(@RequestBody Employee employee){
    int rows = employeeService.insert(employee);
    if(rows > 0){
        return Result.success();
    }
    return Result.error("添加失败");
}

@PutMapping
public Result<Void> update(@RequestBody Employee employee){
    int rows = employeeService.update(employee);
    if(rows > 0){
        return Result.success();
    }
    return Result.error("员工不存在");
}
```

### 为什么只改 Controller，不改 Service
- Service 层返回 `int rows` 是在"报告数据库影响了几行"，这是给 Controller 判断用的，跟 HTTP 响应无关，保持原样。
- Controller 才负责"把结果翻译成 JSON 发给前端"，所以泛型声明只在 Controller 层调整。

### 记忆口诀
> **带数据用真类型，不带数据用 Void；**
> **增删改用 Void，查询登录写实体。**

## ❓ 疑问：为什么"第一次"添加就返回 code 0，数据库里却多了数据？

### 结论：那次 code 0 的请求**根本没有插入数据**
回看 CategoryServiceImpl 的顺序：
```java
Category exist = categoryMapper.getByName(categoryDTO.getName());
if (exist != null) {
    return 0;                    // ← 在这里就"撤"了，下面一行都不会跑
}
...
return categoryMapper.insert(category);   // ← 只有走到这里才插库
```
**查重在 insert 前面**。所以：
- 返回 code 0 ⇒ 这条请求**一定是撞了重名**，它自己一条数据都没插
- 数据库里那条数据 ⇒ 一定是**另一条请求**插进去的

### 用时间戳破案
| 时间 | 发生了什么 |
|---|---|
| 16:19:21 | 某条请求插入成功 → 数据库里出现「川菜」，这条返回的是 **code 1** |
| 16:19:45 | 你看到的那条响应 → code 0（名字已经存在了） |

两条相差 **24 秒**，说明是**两次不同的请求**。你的"第一次"其实已经是第二次了 —— 第一次的响应要么没细看，要么被覆盖了。

### 实测复现（2026-10-12，用全新名字"临时测试菜"打的）
```
第1次: {"code":1,"msg":"操作成功","data":null}      ← 新名字，插库成功
第2次: {"code":0,"msg":"分类名称已存在","data":null}  ← 同一个名字，查重拦下
```
（测完把那行临时数据删掉了，数据库恢复原样）

### 为什么容易"不知不觉发两次"
IDEA 的 .http 文件里，如果点了 **"运行全部请求"**（文件顶部那个双箭头），②③ 会**连着跑**：
② 插入成功 → ③ 同名被拦 → 屏幕上留下来的往往是**最后一条**响应，看着就像"我第一次发就失败了"。
想只发一条，就点**单个请求 URL 左边那个小 ▶**。

### 📌 以后自己判断"谁插的"两招
1. 看数据库那条记录的 `create_time`，跟你发请求的时间对齐
2. 请求前先 `SELECT * FROM category;` 看一眼，请求后再看一次，多出来哪条就是这次插的

### 🧠 记住这句话
> **查重在前、插入在后 —— 能返回"已存在"的请求，必然是没插成功的那一条。**

# 第 4 步：分页查询（概念先讲清）

## 一、为什么需要分页

现实类比：外卖 App 后台有 **几千道菜**。
- 不分页 = 一次性把几千行全查出来发给浏览器 → 页面卡死、流量爆炸、前端渲染不动
- 分页 = 一次只给 **一页**（比如 10 条），用户点"下一页"再要下一段

**数据库里的分页靠 `LIMIT` 完成** —— 只把"这一段"数据从硬盘捞出来，而不是全查完再截断。

## 二、分页的三要素

| 要素 | 谁提供 | 例子 |
|---|---|---|
| `page` 第几页 | 前端传 | `?page=2` |
| `pageSize` 每页几条 | 前端传 | `&pageSize=10` |
| `total` 总共多少条 | 后端查出来返回 | 25 |

前端拿到 `total` 和 `pageSize` 才能算出"一共有 3 页"、画出页码。

## 三、LIMIT 的关键理解：起始下标从 0 开始

```sql
LIMIT 起始下标, 条数
```
**起始下标 = (page - 1) × pageSize**

| 想要 | 起始下标 | SQL |
|---|---|---|
| 第 1 页，每页 10 条 | (1-1)×10 = **0** | `LIMIT 0, 10` |
| 第 2 页，每页 10 条 | (2-1)×10 = **10** | `LIMIT 10, 10` |
| 第 3 页，每页 10 条 | (3-1)×10 = **20** | `LIMIT 20, 10` |

⚠️ 最常见的错误：以为 `LIMIT 1, 10` 是"第 1 页"。**不是**，那是"从第 2 条开始取 10 条"。
（所以第 1 页必须算成下标 0）

## 四、一次分页要查两条 SQL

| # | 查什么 | 作用 |
|---|---|---|
| ① | `SELECT ... LIMIT ?, ?` | 拿**当前这一页**的数据 |
| ② | `SELECT COUNT(*) ...` | 拿**总数**，给前端算页码 |

**为什么必须查两次**：`LIMIT` 只给你一小段，光看这 10 条根本不知道总共有多少条。

## 五、返回给前端的形状（黑马标准）

```json
{
  "total": 25,
  "records": [ {分类1}, {分类2}, ... ]
}
```

所以需要一个"装分页结果"的类：**PageResult**（两个字段就够了：`total` 和 `records`）。
项目里放在 `com.sky.skytakeout.common.PageResult`，和 `Result` 做邻居。

## 六、筛选条件（可选但要有）

后台分类管理页顶部有搜索框，所以 SQL 要支持按条件过滤：

| 条件 | SQL 片段 | 说明 |
|---|---|---|
| 分类名（模糊匹配） | `name LIKE CONCAT('%', #{name}, '%')` | 用 `CONCAT` 拼 % 号，**不直接字符串拼接**（防注入） |
| 分类类型（精确匹配） | `type = #{type}` | 1 菜品分类 / 2 套餐分类 |

排序：`ORDER BY sort ASC, create_time DESC` —— sort 小的排前面，sort 相同时新加的排前面。

## 七、关于 PageHelper 插件（视频里的写法）

黑马视频在分页时用了 `PageHelper.startPage(page, pageSize)`，**不需要在 XML 里写 LIMIT**，
插件会自动帮你 ①改 SQL 加 LIMIT ②再跑一次 count ③把结果打包成 `Page`。

它属于"魔法写法"：**先手写一遍 LIMIT 分页，理解插件到底替你做了什么**，之后再看插件就秒懂。

⚠️ 目前项目 **Spring Boot 3.2.5**，而本机 Maven 仓库里的 pagehelper 是 4.x 版（它是给 Spring Boot 4 用的），
版本对不上，所以现在**不引入这个插件**，先手写。

## 八、第 4 步的执行顺序（拆解）

1. **Navicat 里把两条 SQL 跑通**（带 LIMIT 的和带 COUNT 的）← 现在做这一步
2. 把跑通的 SQL 抄进 `CategoryMapper.xml`（`<select id="list">` + `<select id="count">`）
3. `CategoryMapper.java` 补/改方法签名（列表要传 offset、pageSize）
4. `PageResult` 类
5. Service：算 offset → 查列表 → 查总数 → 装进 PageResult
6. Controller：`@RequestParam` 接收 page / pageSize / name / type
7. 测试 + Navicat 对账

## 🧠 本步口诀

> **起始下标 = (page-1) × pageSize，第 1 页是 0 不是 1；**
> **列表查一段，count 查总数，两个一起才叫分页。**

## ⚠️ 踩坑：Navicat 里直接跑带 `?` 的 SQL 报 1064

```
1064 - You have an error in your SQL syntax ... near '?, ?' at line 5
```

### 原因：`?` 是"占位符"，不是"参数"
`?` 表示"这里**待会儿**会有人填一个真实的值"，它只对**数据库驱动**（JDBC/MyBatis）有意义。

在 Navicat 里直接执行时，**没有任何人去填这个 `?`**，MySQL 收到一条不完整的 SQL，就说语法错误。

### 正确做法（Navicat 里要写死具体数字）
```sql
SELECT * FROM category
WHERE name LIKE CONCAT('%', '菜', '%') AND type = 1
ORDER BY sort ASC, create_time DESC
LIMIT 10, 10;        -- 第 2 页、每页 10 条：(2-1)×10 = 10
```

### 📌 三条链路的角色分工（重要）

| 位置 | 写法 | 谁把值填进去 |
|---|---|---|
| Navicat 手写验证 | `LIMIT 10, 10`（写死） | 你自己 |
| Mapper XML | `LIMIT #{offset}, #{pageSize}` | **MyBatis**：把 `#{xxx}` 换成 `?`，再交给 JDBC 填真实值 |
| JDBC 真正执行的 SQL | `LIMIT ?, ?` | 驱动/数据库 |

所以：**`#{}` 是写给 MyBatis 看的语法，`?` 是写给 JDBC 看的语法，Navicat 里两个都不能用，必须写死具体值。**

### 为什么程序里要用 `?` 而不用拼字符串
用占位符，值是通过"参数通道"传进去的，**不会被当成 SQL 代码解析** → 天然防 SQL 注入。
拼接字符串（`"... LIMIT " + offset + ", " + pageSize`）就是把数据当代码塞进 SQL，危险。

# 第 4 步 · 第 2 小步：把 SQL 搬进 CategoryMapper.xml

## 三处新知识（第一次见）

### ① `resultType` —— 告诉 MyBatis "每行结果装进哪个类"
```xml
<select id="list" resultType="com.sky.skytakeout.entity.Category">
```
- 查出来的每一行 → 自动 new 一个 `Category` 对象，把列值塞进去
- 查询返回**多行**，但 `resultType` 依然写**一个对象**的类型（MyBatis 自己会装成 List）
- `count` 查出来是个数字 → `resultType="int"`
- ⚠️ 全靠 `map-underscore-to-camel-case: true`（yml 里配过），`create_time` 才会自动对上 `createTime`

### ② `<where>` + `<if>` —— 动态条件
```xml
<where>
    <if test="name != null and name != ''">
        AND name LIKE CONCAT('%', #{name}, '%')
    </if>
    <if test="type != null">
        AND type = #{type}
    </if>
</where>
```
`<where>` 的两个作用：
1. 如果里面**一个条件都没成立** → 它连 `WHERE` 这个词都不吐出来（否则会变成 `SELECT * FROM category WHERE ORDER BY ...` 语法错误）
2. 如果第一个成立的条件开头带着 `AND` → 自动把这个多余的 `AND` 吃掉

所以每个条件前都能放心写 `AND`，不用管谁是第一个。

### ③ `@Param` —— 多参数时必须起名字
```java
List<Category> list(@Param("name") String name,
                    @Param("type") Integer type,
                    @Param("offset") Integer offset,
                    @Param("pageSize") Integer pageSize);
```
- 参数只有**一个**时（比如 `getById(Long id)`），XML 里随便写 `#{id}` 都能用
- 参数有**多个**时，MyBatis 不知道该叫谁什么，只能给 `param1/param2/arg0/arg1` 这种丑名字 → **必须用 `@Param("名字")` 起名**，XML 里才能写 `#{名字}`
- `@Param` 来自 `org.apache.ibatis.annotations.Param`

## 对应的 Mapper 接口（两个方法）
```java
List<Category> list(@Param("name") String name,
                    @Param("type") Integer type,
                    @Param("offset") Integer offset,
                    @Param("pageSize") Integer pageSize);

int count(@Param("name") String name, @Param("type") Integer type);
```

## 对应的 XML
```xml
<mapper namespace="com.sky.skytakeout.mapper.CategoryMapper">

    <select id="count" resultType="int">
        SELECT COUNT(*) FROM category
        <where>
            <if test="name != null and name != ''">
                AND name LIKE CONCAT('%', #{name}, '%')
            </if>
            <if test="type != null">
                AND type = #{type}
            </if>
        </where>
    </select>

    <select id="list" resultType="com.sky.skytakeout.entity.Category">
        SELECT * FROM category
        <where>
            <if test="name != null and name != ''">
                AND name LIKE CONCAT('%', #{name}, '%')
            </if>
            <if test="type != null">
                AND type = #{type}
            </if>
        </where>
        ORDER BY sort ASC, create_time DESC
        LIMIT #{offset}, #{pageSize}
    </select>

</mapper>
```

## 📌 为什么视频里方法只有一个参数，我们却有四个
视频用 PageHelper 插件，只要把 `page/pageSize` 交给 `PageHelper.startPage()`，**插件自己往 SQL 尾巴上贴 LIMIT**，
所以 Mapper 方法只收 `Category` 一个参数就够了。

我们手写，就得**自己把 offset 和 pageSize 传进去** —— 这几行代码就是插件替你省掉的活。

## ❓ 这两个是干嘛用的？

### 情况 A：指 `list` 和 `count` 这两条 select

| 谁 | 查什么 | 返回什么 | 对应前端要的哪个数 |
|---|---|---|---|
| `list` | 当前这一页的数据 | `List<Category>`（很多行） | `records` |
| `count` | 满足条件的**总条数** | 一个数字 | `total` |

**为什么必须两条**：分页要交给前端两样东西 —— "这一页有什么" + "一共有多少"。
只有 `list` → 前端不知道总共有几页；只有 `count` → 前端没有内容可显示。

类比翻书：`list` = 翻到第 3 页看这页的内容；`count` = 看这本书总共多少页。

⚠️ **两条 SQL 的筛选条件必须一模一样**。
如果 `count` 带了 `type = 1` 而 `list` 没带，就会算出"总数 50 条"，但页面上只显示菜品分类的 10 条 → 页码全错。

### 情况 B：指 `ORDER BY ...` 和 `LIMIT ...` 这两行

#### `ORDER BY sort ASC, create_time DESC` —— 决定"谁排前面"
- **不加排序 = 翻页会乱**：数据库返回顺序本身不保证稳定，第 2 页可能又出现第 1 页的内容、或者漏掉几条
- `sort ASC`：sort 小的在前（后台管理员手动拖出来的顺序）
- `create_time DESC`：sort 相同时，新增的排前面
- **多个字段是"多级排序"**：先按第一个排，第一个相同再看第二个（跟 Excel 多级排序一个道理）

> 📌 口诀：**要分页，必排序。** 分页 + 无排序 = 玄学翻页。

#### `LIMIT #{offset}, #{pageSize}` —— 决定"只取哪一段"
- 它是分页的本体：`LIMIT 0, 10` = 从第 0 条开始取 10 条
- `offset` 由后端算：`(page - 1) × pageSize`（第 1 页是 0，第 2 页是 10……）
- 没有 LIMIT → 一次把全表发过去，分页就没意义了

⚠️ 注意：`count` 那条**不能**带 `LIMIT`（总数不受分页影响），`list` 这条**必须**带。

### 谁提供这几个值
| 值 | 谁算/谁给 |
|---|---|
| `page`、`pageSize` | 前端在 URL 上带过来（Controller 用 `@RequestParam` 接） |
| `offset` | Service 算：`(page-1) × pageSize` |
| `name`、`type` | 前端搜索框带过来（可空） |

## 🐛 核对：list 这条有两处错（2026-10-12）

### 错误 1：`SELECT COUNT(*)` 应该是 `SELECT *`
```xml
<select id="list" resultType="com.sky.skytakeout.entity.Category">
    SELECT COUNT(*) FROM category     <!-- ❌ 这是 count 的写法，复制粘贴带过来了 -->
```
**危险之处：这条 SQL 语法完全合法，MyBatis 不会报错。**
实测（Navicat）：
```sql
SELECT COUNT(*) FROM category WHERE name LIKE CONCAT('%','菜','%') AND type=1 LIMIT 0,10;
-- 结果：只有一行，内容是数字 1
```
于是：
- `list` 查出来是"一个数字"而不是"一堆分类行"
- MyBatis 拿这个列名 `COUNT(*)` 去匹配 `Category` 的属性 → **一个都对不上**
- 结果 `records` 里装了一个**全字段为 null 的空壳对象** `{}`

**症状**：接口 200、不报错、前端看到 `records: [{}]` —— 最恶心的一类 bug。
> 📌 教训：**不报错的 bug 最难查**。看到结果"形状不对"，先回去看 SQL 到底 SELECT 了什么列。

### 错误 2：`IMIT` 少了一个 L
```xml
IMIT #{offset}, #{pageSize}     <!-- ❌ -->
LIMIT #{offset}, #{pageSize}    <!-- ✅ -->
```
这个会直接报语法错误（反而好，一炸就知道）。
> 教训：MyBatis 的 XML **不检查 SQL**，IDE 也检查不出来，全靠自己看 + 真跑一次。

### 总结：写 XML 时最容易"静悄悄错"的三个地方
| 坑 | 症状 |
|---|---|
| SELECT 列写错（复制粘贴串了） | 不报错，结果形状不对 |
| `#{}` 名字和 `@Param` 对不上 | 运行时报错 `Parameter 'xxx' not found` |
| SQL 拼错（IMIT / FROM 丢了） | 语法错误 |

# 第 4 步 · 第 3 小步：Service 层（分页的"大脑"）

## ① 先建一个 DTO 装"前端传来的分页参数"
`com.sky.skytakeout.dto.CategoryPageQueryDTO`
```java
@Data
public class CategoryPageQueryDTO {
    private Integer page = 1;        // 第几页，默认第 1 页
    private Integer pageSize = 10;   // 每页几条，默认 10 条
    private String name;             // 分类名（模糊查，可不传）
    private Integer type;            // 分类类型（可不传）
}
```

### 为什么参数要"打包成 DTO"
1. **参数超过 3 个就该打包**：`(page, pageSize, name, type)` 四个散着传，方法签名又长又容易传错位
2. **Spring 能自动绑定**：Controller 的参数写成 `CategoryPageQueryDTO dto`（不加 `@RequestBody`），
   Spring 会拿 URL 上的 `?page=2&pageSize=10&name=菜` **按名字对名字**填进对象的同名字段
3. 以后分页查询条件变多，只改 DTO，不用改方法签名

### 字段初值 = 默认值
`private Integer page = 1;` 表示：前端传了就用前端的，**没传就保持 1**。
好处：前端忘了传 `pageSize`，也绝不会出现 `LIMIT (0-1)*0` 这种把 SQL 搞炸的情况。

⚠️ 和视频的差别：黑马原版这里用的是 `private int page;`（基本类型，初值 0，没有默认值）。
我们改成 `Integer` + 默认值，更抗造。

## ② Service 接口加一个方法
```java
PageResult<Category> pageQuery(CategoryPageQueryDTO categoryPageQueryDTO);
```
- 返回类型 `PageResult<Category>`：分页结果的"外壳"是 PageResult，"里面装的东西"是 Category
- 参数只有一个 DTO：干净

## ③ Service 实现的 5 步配方（这就是分页的全部逻辑）
```java
@Override
public PageResult<Category> pageQuery(CategoryPageQueryDTO dto) {
    // ① 取出前端给的值
    Integer page = dto.getPage();
    Integer pageSize = dto.getPageSize();

    // ② 算起始下标（分页的核心公式）
    int offset = (page - 1) * pageSize;

    // ③ 查"这一页的数据"
    List<Category> records = categoryMapper.list(dto.getName(), dto.getType(), offset, pageSize);

    // ④ 查"总共多少条"（条件必须和 ③ 一模一样）
    int total = categoryMapper.count(dto.getName(), dto.getType());

    // ⑤ 组装成 PageResult 返回
    PageResult<Category> pageResult = new PageResult<>();
    pageResult.setTotal((long) total);
    pageResult.setRecords(records);
    return pageResult;
}
```

### 逐行理解
| 行 | 在干嘛 | 现实类比 |
|---|---|---|
| ① | 拿到"第几页、每页几条、搜什么" | 读者说"我要第 3 页，每页 10 条" |
| ② | 把"第几页"换算成"从第几条开始" | 把"第 3 页"换算成"从第 21 条开始" |
| ③ | 只取这一段 | 翻到第 3 页，看这页内容 |
| ④ | 数一共有多少条 | 看这本书一共多少页 |
| ⑤ | 两样东西打包交给前端 | 把"这页内容 + 总页数"写在一张纸条上 |

### ⚠️ 两个易错点
1. **③④ 的条件必须一致**：都传 `dto.getName()` 和 `dto.getType()`。少传一个，页码就全错。
2. **offset 必须是最先算的**：忘了算、直接把 page 当 offset 用，第 1 页就会变成 `LIMIT 1, 10`（少显示第一条）。

### 顺序问题
先查列表还是先查总数，**都行**，数据库不会因为顺序不同给出不同结果。
（如果哪天真遇到"并发新增导致 total 和 records 对不上"，那属于事务/一致性问题，现在不用管。）

## ④ 数据流全景（第 4 步走完就是这条链）
```
前端 ?page=2&pageSize=10&name=菜
   ↓ Spring 自动绑定
CategoryPageQueryDTO
   ↓ Controller
Service.pageQuery()  → 算 offset
   ↓
CategoryMapper.list(...)  → 查这一页
CategoryMapper.count(...) → 查总数
   ↓
PageResult<Category>{ total, records }
   ↓ Controller 再套一层 → Result<PageResult<Category>>
前端
```

## ✅ 核对：Service 层 5 步全对（2026-10-12）
- `CategoryService` 接口：`PageResult<Category> pageQuery(CategoryPageQueryDTO)` ✅
- `CategoryServiceImpl`：取 page/pageSize → 算 offset → 查 list → 查 count → 组装 PageResult ✅
- `PageResult<Category> pageResult = new PageResult<>();` 的写法也对（右边不用重复写类型）✅

### ⚠️ 但 DTO 少了两个默认值 —— 这会导致 500
```java
private Integer page;       // ← 没写 = 1
private Integer pageSize;   // ← 没写 = 10
```
**症状**：前端如果不带 `?page=1&pageSize=10`，两个字段就是 `null`，然后
```java
int offset = (page - 1) * pageSize;   // null 参与运算 → 自动拆箱 → NullPointerException → 500
```
**修法**：给字段加初值
```java
private Integer page = 1;
private Integer pageSize = 10;
```
> 📌 一个规律：**包装类型（Integer）可以是 null，基本类型（int）不能。**
> 只要一个 `Integer` 字段参与了算术运算，就要先想"它会不会是 null"。

## ✅ 第 4 小步：Controller（最后一块）

```java
@GetMapping("/page")
public Result<PageResult<Category>> page(CategoryPageQueryDTO categoryPageQueryDTO){
    PageResult<Category> pageResult = categoryService.pageQuery(categoryPageQueryDTO);
    return Result.success(pageResult);
}
```

### 三个关键点

#### ① 参数上**不加** `@RequestBody`
| 场景 | 参数在哪 | 用什么接 |
|---|---|---|
| GET 请求 `?page=2&pageSize=10` | URL 查询字符串 | **什么都不加**，Spring 按"名字对名字"填进 DTO 字段 |
| POST 请求 `{ "username": "admin" }` | 请求体（JSON） | `@RequestBody` |

所以 GET + DTO = 自动绑定；字段名必须和 URL 参数名一致（`page` / `pageSize` / `name` / `type`）。

#### ② 泛型套泛型：`Result<PageResult<Category>>`
- 最外层 `Result` = 统一信封（code / msg / data）—— 所有接口都一样
- 中间 `PageResult` = 分页内容（total / records）
- 最里层 `Category` = records 里每个元素是什么
- 拆开读：**"信封里装了一个分页结果，分页结果里装了一堆分类"**

#### ③ 路径 `/page` 是怎么来的
类上是 `@RequestMapping("/category")`，方法上是 `@GetMapping("/page")`
→ 拼起来就是 `GET /category/page`（类上的当"前缀"，方法上的当"后缀"）

### Controller 层最终数据流
```
GET /category/page?page=1&pageSize=10
   ↓ Spring 自动绑定
CategoryPageQueryDTO
   ↓
categoryService.pageQuery(dto)
   ↓
Result.success(pageResult)
   ↓
{ "code":1, "msg":"操作成功", "data": { "total":6, "records":[ ... ] } }
```

## ❓ `pageQuery` 是什么意思？

**就是"分页查询"的英文写法**（page = 分页，query = 查询）。

⚠️ 关键：**它不是关键字、不是注解、不是框架规定的方法名** —— 纯粹是我们自己起的名字。
改成 `page`、`queryPage`、`listByPage` 都能跑，程序完全不挑名字。

### 那为什么还要认真起名
因为**代码是给人看的**。半年后你回头看 `pageQuery`，一眼知道"这是分页查询"；
如果叫 `aaa` 或者 `getData2`，就得点进去读一遍才知道。

> 方法名不影响"能不能跑"，只影响"看不看得懂"。

### 项目里已经用过的命名套路

| 干什么 | 常用名字 | 项目里的例子 |
|---|---|---|
| 查一条 | `getXxx` / `findXxx` / `getById` | `findById`、`getByName` |
| 查一堆 | `list` / `listXxx` / `findAll` | `findAll`、`list`（Mapper 里的） |
| **分页查** | **`pageQuery`** / `page` | **`pageQuery`** |
| 新增 | `insert` / `save` / `add` | `insert` |
| 修改 | `update` | `update` |
| 删除 | `deleteById` / `remove` | `deleteById` |
| 登录 | `login` | `login` |

### 为什么 Mapper 里叫 `list`、`count`，Service 里叫 `pageQuery`
- Mapper 的 `list` / `count` 是**两个具体的数据库动作**（取一段数据 / 数总数）
- Service 的 `pageQuery` 是**一个完整的业务动作**（它内部会调用上面那两个）
- 一个业务动作可能要靠多个数据库动作拼出来 —— 名字层级不一样，很正常

### 命名小规则（背下来不吃亏）
1. **动词开头**：`insert`、`update`、`pageQuery`
2. **说清对象**：`pageQuery` / `findById` / `deleteById`
3. **同一个项目里保持统一**：都叫 `insert` 就别某个地方突然叫 `add`

## ❓ 为什么 GET 分页不用 `@RequestBody`？

### 一句话
**因为参数根本不在"请求体"里，它在 URL 上。**
`@RequestBody` 只负责"把请求体读出来变成对象" —— 请求体里没东西，自然不用它。

### 拆开看两个请求长什么样
```
GET  /category/page?page=1&pageSize=10&name=菜        ← 参数贴在 URL 后面（查询字符串）
（这个请求没有请求体，或者说不该有）

POST /employee/login
Content-Type: application/json
{ "username": "admin", "password": "123456" }        ← 参数在请求体里（一坨 JSON）
```

### 那么 DTO 对象是谁 new 出来的？
**是 Spring 自己 new 的。** 流程是：
1. Spring 看到方法参数类型是 `CategoryPageQueryDTO`（一个自定义对象）
2. 它就 `new CategoryPageQueryDTO()`（此时字段全是默认值）
3. 然后拿 URL 上的参数名去**对**字段名：
   - `?page=1` → 调用 `setPage(1)`
   - `?pageSize=10` → 调用 `setPageSize(10)`
   - `?name=菜` → 调用 `setName("菜")`
   - 没传的字段保持原样（这就是为什么默认值 `= 1` / `= 10` 有用）
4. 把这个对象传给你的方法

这个过程叫 **数据绑定（Data Binding）**，**不是 JSON 反序列化**。
两者唯一的相似点是：最后都得到一个"装满值的 Java 对象"。

### 对照表（三种参数位置，三种接法）

| 数据放在哪 | 例子 | 怎么接 | 谁来解析 |
|---|---|---|---|
| **请求体**（JSON） | `{ "username":"admin" }` | `@RequestBody EmployeeLoginDTO dto` | Jackson（JSON → Java 对象） |
| **URL 问号后面** | `?page=1&pageSize=10` | 参数不加注解（单个用 `@RequestParam`） | Spring 按名字对名字 setXxx |
| **URL 路径里** | `/employee/7` | `@PathVariable Long id` | Spring 按占位符取 |

### 一个关键认知：分界线是"数据在哪"，不是"GET 还是 POST"
- GET 也能带请求体 → 但浏览器/网关/代理经常丢掉它，**所以规范上不这么干**
- POST 也能用 URL 参数（`POST /x?a=1`）→ 完全合法
- 所以真正决定用不用 `@RequestBody` 的，是**数据到底放在哪里**

### 如果给 GET 硬加 `@RequestBody` 会怎样
Spring 读不到请求体 → 直接抛错（类似 `Required request body is missing`），**400 错误**。
前端明明只想传两个查询参数，你却要求它"交出一坨 JSON"，自然对不上。

### 类比
- `@RequestBody` = **拆箱子**：箱子里装着一坨 JSON，得用 Jackson 拆开
- URL 参数 = **箱子外面的快递面单**：不拆箱子也能看到"收件人、电话"
- 分页参数就贴在面单上，所以**不需要拆箱子**

### 🔍 排查技巧（以后很有用）
如果接口收到参数后**字段全是 null**，按这个顺序查：
1. 前端到底把参数放在哪了？（URL？还是 body？）
2. 后端注解对上了吗？（URL 参数配了 `@RequestBody` = 错配）
3. 名字对得上吗？（URL 里是 `pageSize`，DTO 字段是 `page_size` = 对不上）

## ❓ 那为什么之前的参数没在 URL 上？

### 一句话
**因为参数放哪是"接口设计"的选择，不是硬性规定。**
放 URL 还是放请求体，取决于这个接口"要干什么"。

### 把项目里所有接口摊开看，规律立刻出现

| 接口 | 参数 | 放在哪 | 为什么这么放 |
|---|---|---|---|
| `GET /employee` | 无 | — | 查全部，不需要条件 |
| `GET /employee/7` | id | **URL 路径里** | 用来标识"要哪一个员工" |
| `DELETE /employee/2` | id | **URL 路径里** | 同上，标识"删哪一个" |
| `GET /category/page?page=1&pageSize=10` | 分页+筛选条件 | **URL 问号后面** | 查询条件，用来"筛"，不改数据 |
| `POST /employee` | 员工一整条（6~7 个字段） | **请求体** | 字段多，而且是"提交一份数据" |
| `PUT /employee` | 员工对象 | **请求体** | 同上，提交要改的内容 |
| `POST /employee/login` | username / password | **请求体** | ⚠️ **密码绝不能出现在 URL 上** |
| `POST /category` | 分类对象 | **请求体** | 提交一份新数据 |

**规律**：
- **URL 上放的是"查什么、要哪一个"**（id、筛选条件、页码）
- **请求体里放的是"要提交的内容"**（一整条数据，尤其是新增/修改/登录）

### URL 参数其实有两种，别混

| 种类 | 写法 | 含义 | 项目里的例子 |
|---|---|---|---|
| **路径参数** | `/employee/7` | 标识"**哪一个**" | `@PathVariable Long id` |
| **查询参数** | `/category/page?page=1` | 描述"**怎么筛、怎么分页**" | 不加注解 / `@RequestParam` |

两种都属于"URL 上"，只是位置不同：一个在**路径**里，一个在**问号后面**。
所以"之前的参数没在 URL 上"这句话要修正一下：**`/employee/7` 的那个 `7` 就在 URL 上**，只是它藏在路径里，不是问号后面。

### 为什么登录的密码不放 URL（重点）
URL 会被记录在很多地方：
- 浏览器历史记录
- 服务器访问日志（nginx 的 access.log 里就有完整 URL）
- 代理/网关日志
- 页面的 Referer 头

密码一旦进了 URL，就等于**在日志里明文留了一份**。
所以登录这种敏感数据必须放请求体，而且现在主流还会全程 HTTPS 加密。

### 还有个体面理由：URL 有长度上限
URL 一般 2000 字符左右就到顶了。要提交一个 20 字段的表单，塞 URL 里根本塞不下。
请求体没有这个限制。

### 补充：GET 也能用 URL 参数，因为它"不改数据"
HTTP 语义上，GET 应该只读、不修改。所以 GET 天然适合"把条件写在 URL 上"：
```
GET /category/page?page=1&pageSize=10&name=菜
→ 一看就知道：查第 1 页、每页 10 条、名字带"菜"
```
这种 URL 是**可以直接书签、直接粘贴给别人**的，这也是它方便的地方。

### 前端（Vue/axios）那边是这样的
```js
// 查询：参数放 params → 自动拼到 URL 上
axios.get('/category/page', { params: { page: 1, pageSize: 10 } })
// 实际请求：GET /category/page?page=1&pageSize=10

// 新增：参数放 data → 自动放进请求体
axios.post('/category', { name: '川菜', type: 1, sort: 10 })
// 实际请求体：{ "name": "川菜", "type": 1, "sort": 10 }
```
前端"放 params 还是放 data"，和后端"用不用 @RequestBody"，**必须配对**：
- `params` ↔ URL 参数 ↔ 后端不加注解
- `data` ↔ 请求体 ↔ 后端 `@RequestBody`

⚠️ 这对不上，后端收到的就是一堆 `null`（或直接 400）。

## ❓ 我怎么知道 URL 上面是什么？什么时候该用 @RequestParam？

### 核心思路（先把这个想通）
**URL 不是"猜"出来的，是"定"出来的。** 三个地方能看到它：

| 从哪看 | 怎么看 | 谁定义的 |
|---|---|---|
| **后端注解** | 类上 `@RequestMapping("/category")` + 方法上 `@GetMapping("/page")` → 拼出 `/category/page` | 后端开发者 |
| **前端代码 / F12** | 浏览器 F12 → Network → 点那个请求 → 看 **Request URL** | 前端怎么调就长什么样 |
| **接口文档** | 黑马给的接口文档（或 yapi）里写着请求路径和参数 | 项目约定 |
| **你自己的 .http 文件** | `GET http://localhost:8080/category/page?page=1&pageSize=3` —— 这一行就是完整 URL | 你自己写的 |

> 在自己做项目时，**URL 就是你自己定的**：你在 .http 里写 `?page=1&pageSize=3`，那这个接口的查询参数就是 page 和 pageSize。

### 实操技巧：让 IDEA 把"所有 URL"打印出来
在 `application.yml` 里加一行，重启项目，控制台会列出每个接口完整路径：
```yaml
logging:
  level:
    org.springframework.web: TRACE
```
启动日志里会看到类似 `Mapped GET [/category/page]` 的行 —— **这就是整个项目所有 URL 的地图**。

---

### 三步判断法（看到接口就知道用哪个注解）

**第一步：看方法上的注解里有没有 `{}` 占位符**
- 有 → `@PathVariable`
  例：`@GetMapping("/{id}")` + `@PathVariable Long id`

**第二步：看是"提交数据"还是"查/筛数据"**
- 提交一整条数据（POST / PUT）→ `@RequestBody`
  例：`@PostMapping` + `@RequestBody Employee employee`

**第三步：剩下的就是"问号后面的查询参数"**
- GET + 筛选/分页条件 → **不加注解**（参数多）或 `@RequestParam`（参数少）

| 判断依据 | 用哪个注解 | 项目里的例子 |
|---|---|---|
| 注解里有 `{}` | `@PathVariable` | `GET /employee/{id}` |
| POST/PUT + 一整条 JSON | `@RequestBody` | `POST /employee`、登录 |
| GET + 问号后面的条件 | 不加注解 / `@RequestParam` | `GET /category/page?page=1` |

---

### `@RequestParam` 的四个常用属性

```java
@RequestParam(defaultValue = "1") Integer page                      // 没传就默认 1
@RequestParam(name = "pageSize") Integer size                       // URL 参数名和变量名不一样时改名
@RequestParam(required = false) String name                         // 可以不传
@RequestParam(value = "type", required = false) Integer type        // 组合
```

### 那 `@RequestParam` 和"直接写 DTO"有什么区别？
**数据来源完全一样**（都是 URL 问号后面的查询参数），区别只在"怎么装"：

| 写法 | 适合场景 | 例子 |
|---|---|---|
| `@RequestParam Integer page` | **参数少（1~2 个）**，一眼看得清 | `GET /employee?status=1` |
| 直接写 DTO 对象 | **参数多（3 个以上）**，打包更清爽 | `GET /category/page?page&pageSize&name&type` |

> 判断口诀：**参数少用 @RequestParam，参数多用 DTO。**
> 你现在的分页有 4 个参数，所以用 DTO；如果只有一个 `id`，用 `@RequestParam` 反而更直接。

### ⚠️ 注意：`@RequestParam` 没写 `defaultValue` 且前端没传时
- 参数类型是**基本类型/包装类型**且 `required=true`（默认）→ 直接 **400 错误**
- 所以要么给 `defaultValue`，要么 `required = false`

### 🔍 反过来验证（最保险的办法）
改完代码别猜，**直接发请求试**：
1. 在 .http 里写 `GET /category/page?page=1&pageSize=3`
2. 如果后端返回的数据对 → 参数接对了
3. 如果 `records` 是空数组、`total` 也不对 → 大概率是**名字没对上**（比如 DTO 字段写成了 `page_size`）

## 二、第 5 题补讲：`@Param` 是干嘛的

**问题**：`list(String name, Integer type, Integer offset, Integer pageSize)` 为什么要每个参数都套 `@Param`？

**原因：Java 编译之后参数名会丢。** `String name` 编译后可能变成 `arg0`，
MyBatis 不知道谁叫 `name`，XML 里 `#{name}` 就炸：

```
BindingException: Parameter 'name' not found.
Available parameters are [arg0, arg1, param1, param2]
```

`@Param("name")` = **给参数贴个名字标签**。

> 📦 类比：快递单写"收件人"快递员不知道给谁，写"张三"才送得到。

### 什么时候不用 @Param

| 情况 | 要 @Param 吗 | `#{}` 里写什么 |
|---|---|---|
| 单参数 + POJO（如 `Category`） | ❌ 不用 | 写**属性名**：`#{name}` `#{sort}` |
| 单参数 + 简单类型（String/Long） | ❌ 不用 | 写啥都行，MyBatis 把唯一的值给你 |
| **多参数** | ✅ **必须** | 写 `@Param` 里起的名字 |

> 所以 `insert(Category category)` 能用 `#{name}` —— 那是因为 `getName()` 存在，**不是**因为有 `@Param`。

## 三、第 7 题补讲：为什么不让前端传 `create_user`

1. **前端能伪造** —— 请求体是用户随便改的，F12/Postman 一改，createUser 就能填 99 或不传
2. **前端根本不知道自己是谁** —— 它手里只有 token，token 是**后端签发、验过签**的
3. 所以审计字段必须由后端从可信来源（token → empId）自己填

> 🚪 类比：进小区门禁不能自己报房号，得**刷卡**（卡是物业发的）。
> `BaseContext.getCurrentId()` 就是"刷完卡的结果"。

⭐ **一句话背下来：前端传来的数据，一律当成"不可信输入"。**

## 四、第 8 题补讲：为什么返回 `PageResult<Category>` 而不是 `List<Category>`

分页要告诉前端三件事：

| 要什么 | `List` 能给吗 |
|---|---|
| ① 这一页的数据 | ✅ |
| ② 一共多少条（total） | ❌ 不能 |
| ③ 一共多少页（= ② ÷ pageSize） | ❌ 算不出来 |

前端分页控件要显示"共 6 条"和页码按钮。只给 `List`，它只知道这一页 3 条，**不知道后面还有没有**。

所以必须包一层：

```json
{ "total": 6, "records": [ {...}, {...}, {...} ] }
```

> 🍜 类比：订单页写"共 12 单，当前第 1 页"，只给 3 单你不知道后面还有没有。

**泛型 `<T>` 的好处**：`PageResult<Employee>` / `<Dish>` / `<Setmeal>` 全用同一个类，不用写 4 遍。

## 五、第 9 题补讲：`<where>` 和 `<if>` 各干嘛的

```xml
<where>
    <if test="name!=null and name!=''">
        AND name LIKE CONCAT('%',#{name},'%')
    </if>
    <if test="type!=null">
        AND type=#{type}
    </if>
</where>
```

### `<if>` = 条件判断
`test` 成立才把那段 SQL 拼进去。没传 name，那段 `AND name LIKE ...` 当没写过。

> 🍔 类比：点餐的"加购"——勾了才有这一项。

### `<where>` = 自动收拾 `WHERE` 关键字（干两件脏活）

| 脏活 | 不写 `<where>` 会怎样 |
|---|---|
| ① 所有 `<if>` 都不成立 → **一个 WHERE 都不写** | `... WHERE ORDER BY ...` → **1064 语法错误** |
| ② 第一个成立的条件以 `AND` 开头 → **自动砍掉那个 AND** | `WHERE AND name LIKE ...` → **1064 语法错误** |

| 传参 | 拼出来的 SQL |
|---|---|
| `name=川`，type 不传 | `WHERE name LIKE '%川%'`（AND 被砍掉）✅ |
| `type=1`，name 不传 | `WHERE type=1` ✅ |
| 都不传 | 没有 WHERE 子句 ✅ |

> 💡 这就解释了黑马视频里为什么要写 `WHERE 1=1` —— 那是**没有 `<where>` 时的土办法**。
> 有了 `<where>`，不用这个笨招了。

## 六、第 10 题补讲：不带 token 请求 `/category/page`

**结果：HTTP 401，而且 Controller 里的代码一行都不会执行。**

```java
String token = request.getHeader(...);   // ① 没带 → token = null
try {
    JwtUtil.parseJWT(secretKey, token);  // ② null 进去 → 抛异常
    return true;                          // ✔ 放行
} catch (Exception e) {
    response.setStatus(401);              // ③ 打 401 标签
    return false;                         // ④ 关门 ← 关键
}
```

`return false` = **门关上了**。请求被拦在门外，Controller / Service / Mapper **一个都不跑**。

> 🏢 类比：写字楼闸机。没刷卡 → 闸机不开，里面任何一间办公室都进不去。

### ⭐ 401 vs 403（以后做权限控制的地基）

| 码 | 意思 | 类比 |
|---|---|---|
| **401** | **你是谁？先登录**（没令牌 / 令牌假 / 令牌过期） | 没有工牌 |
| **403** | **知道你是谁，但你没这个权限** | 有工牌，但进不去财务室 |

# 第 5 步：启用 / 禁用分类（2026-10-14）

## 一、这个接口是干什么的（先懂业务）

餐厅的菜单分类（凉菜 / 热菜 / 汤类）需要能"下架"和"上架"。

- `status = 1` → 启用（上架）
- `status = 0` → 禁用（下架）

管理端列表里，每一行都有一个"启用 / 禁用"按钮。点一下，前端要告诉后端两件事：

1. **改哪个分类** → `id`
2. **改成什么状态** → `status`（0 或 1）

## 二、接口长什么样

```
POST /category/status/{status}?id=8
```

实际发出去的样子：

```
POST /category/status/0?id=8     ← 把 8 号分类禁用
POST /category/status/1?id=8     ← 把 8 号分类启用
```

> 黑马原版是 `POST /admin/category/status/{status}`，我们项目把 `/admin` 省略了。

## 三、为什么一个值放路径、一个值放 `?` 后面

| 位置 | 例子 | 用什么接 | 这次是谁 |
|---|---|---|---|
| 路径里的 `{}` | `/status/**0**` | `@PathVariable` | status |
| `?` 后面的键值 | `?**id=8**` | `@RequestParam` | id |
| 请求体 JSON | `{ "id": 8 }` | `@RequestBody` | 这次不是 |

### 🔑 判断标准（背下来）

> **路径里那段值是"要写入的结果 / 要操作的对象" → 用 `{xxx}` + `@PathVariable`**
> **路径里那段值是"筛选用 / 附带条件" → 放 `?` 后面 → `@RequestParam` 或 DTO 自动接**

对照理解：

- `/category/page`：动作永远是"查"，`page/pageSize/name/type` 都只是**筛选条件** → 全放 `?`
- `/category/status/{status}`：路径里的 `0/1` **本身就是要写进数据库的值**，不是筛选 → 放路径

## 四、`{status}` 到底是什么？—— 占位符，不是字面文字

| 写法 | 含义 |
|---|---|
| `/page` | **固定**路径，就叫 page |
| `/status` | **固定**路径，就叫 status |
| `/status/{status}` | `/status` 后面**还有一段，内容会变**，`{}` 是"占坑" |

`{}` 里的 `status` 只是"**坑的名字**"。Spring 心里想的是：

> "收到请求后，把 `/status/` 后面那一段抠出来，交给一个叫 `status` 的参数。"

所以：

- 前端发 `/category/status/**0**` → 抠出 `0` → `@PathVariable Integer status` 拿到 **0**
- 前端发 `/category/status/**1**` → 抠出 `1` → 拿到 **1**

### ❓ 那为什么不直接写 `/status`，像 `/page` 一样？

**也能跑，但 `status` 的值就得挪到别处去**（比如 `?status=0`），而且 `@PathVariable` 就**没东西可以取了** —— 因为没有 `{}`，Spring 不知道要从路径里抠任何东西。

黑马选"把值编进路径"，是为了 **URL 可读**：`/status/0` 一眼看出"要设成 0"。

```
POST /category/status/0    → 把状态设成 0（禁用）
POST /category/status/1    → 把状态设成 1（启用）
```

> ⚠️ **实际发请求的 URL 里没有花括号**，花括号只存在于**代码里**，用来告诉 Spring "这里有一段是活的"。

## 五、三层怎么写

### ① Mapper 层：`CategoryMapper.java`

```java
@Update("UPDATE category SET status=#{status},update_time=#{updateTime},update_user=#{updateUser} WHERE id=#{id}")
void updateStatus(Category category);
```

**为什么这里用注解 `@Update`，而 list / count 却写在 XML 里？**

| SQL 特点 | 写哪儿 |
|---|---|
| **固定、简洁**（字段永远这几个） | 直接写注解里，省事 |
| **要动态拼**（有 `<if>` 条件） | 搬到 XML |

> 📌 记忆：**SQL 固定简洁 → 注解；SQL 要动态拼 → XML。**

**参数为什么是 `Category` 对象？** 因为一次要传 4 个值（id、status、updateTime、updateUser），用对象装进去，`#{status}` / `#{id}` 正好对属性名。

### ② Service 层

接口 `CategoryService.java` 加一行：

```java
void updateStatus(Integer status, Long id);
```

实现 `CategoryServiceImpl.java` 加方法：

```java
@Override
public void updateStatus(Integer status, Long id) {

    Category category = new Category();
    category.setId(id);
    category.setStatus(status);
    category.setUpdateTime(LocalDateTime.now());
    category.setUpdateUser(BaseContext.getCurrentId());

    categoryMapper.updateStatus(category);
}
```

三个理解点：

1. **为什么只 new 一个空 Category、填 4 个字段就够？** 因为 Mapper 那条 SQL 只用到这 4 个值。其他字段（name/sort/type）SQL 里根本没提，填了也白填 —— **只填 SQL 要用到的**。
2. **`BaseContext.getCurrentId()` 从哪来？** 第 10 课做的 ThreadLocal "储物柜"。拦截器验完 token 把 empId 塞进去了，这里取出来当 `updateUser`（记录"是谁改的"）。**不是前端传的** —— 前端传的一律不可信。
3. **为什么返回 `void`？** `insert` 返回行数是因为 Controller 要判断重名（0 = 重复）。这个接口没有"失败分支"要给前端区分，用不到行数，就返回 `void`。

**为什么 Service 参数是 `(Integer status, Long id)`，Mapper 却是 `Category` 对象？**

| 层 | 手里有什么 | 干什么 |
|---|---|---|
| Controller → Service | 两个零散值 | 原样递过去 |
| Service 内部 | 拿到零散值 | **组装**成完整 Category 再交给 Mapper |

> 📌 一句话：**Service 是"组装车间"，Mapper 只负责拿成品去执行 SQL。**

### ③ Controller 层：`CategoryController.java`

```java
@PostMapping("/status/{status}")
public Result<Void> updateStatus(@PathVariable Integer status,@RequestParam("id") Long id){
    categoryService.updateStatus(status,id);
    return Result.success();
}
```

四个理解点：

1. **路径为什么只写 `"/status/{status}"`？** 类头上已有 `@RequestMapping("/category")`，Spring 会拼起来：`/category` + `/status/{status}` = `/category/status/{status}`。
2. **`@PathVariable Integer status`** —— 把路径里 `{status}` 那段抠出来。**坑名必须和参数名对上**（也叫 `{status}` ↔ 参数也叫 `status`），不对上就得写 `@PathVariable("坑名")`。
3. **`@RequestParam("id")`** —— 取 `?id=8`。**为什么要显式写名字？** 因为 **Java 编译成 class 后参数名默认会丢**（`id` 可能变 `arg0`），框架靠"名字"对号，名字丢了就对不上。这和 MyBatis 那题（`@Param`）**是同一个原因**。（黑马视频里没写括号也能跑，是因为 Spring Boot 默认保留了参数名，但显式写更稳。）
4. **为什么返回 `Result<Void>`，`success()` 不带参数？** 这个接口**没有数据给前端**，前端只想知道成功没成功。成功 → `code=1`；失败 → 拦截器直接挡在前面给 401，根本到不了这里。

> `@PathVariable`、`@RequestParam`、`@PostMapping` 都在类头 `import org.springframework.web.bind.annotation.*` 里，不用额外 import。

## 六、⚠️ 踩坑：写成了 `@PutMapping`（2026-10-14）

实写时第一版写的是 `@PutMapping`，**直觉是对的**（RESTful 里 PUT 表示"更新"），但**黑马用的是 POST**。

| 方法 | 通常表示 |
|---|---|
| GET | 查 |
| POST | 新增 / **执行一个动作** |
| PUT | 更新（整体替换资源） |
| DELETE | 删 |

**黑马为什么用 POST？** 因为它把"启用 / 禁用"当成**"执行一个动作"**，而不是"替换一个资源"。路径 `/status/0` 读起来就是"执行：把状态置为 0" —— 动作类操作，RESTful 里一般用 POST。（PUT 语义下路径通常长成 `/category/8/status` 那种资源的样子。）

### 🔴 最关键的一点：前后端必须一致，否则 405

**这不是"哪个更好"的问题，是"必须对上"的问题。**

之前踩过的坑：

```
{"status": 405,"error": "Method Not Allowed","path": "/employee"}
```

**405 = 这个地址我知道，但它不接受你用的这个 HTTP 方法。** 后端写 `@PutMapping`、前端发 POST（或反过来），就直接 405，跟功能写没写对无关。

> ✅ 结论：**跟黑马统一用 `@PostMapping`**，学习阶段方便对照。改法就是把 `@PutMapping` 改成 `@PostMapping`，**只改这一个词**。

## 七、测试：让 IDEA 自动存 token（省去手动复制）

以前测接口要手动复制那一长串 token，现在可以让 IDEA **自动存**：

```http
### 1. 登录（跑完会自动把 token 存起来）
POST http://localhost:8080/employee/login
Content-Type: application/json

{
  "username": "admin",
  "password": "123456"
}

> {%
    client.global.set("token", response.body.data.token);
%}


### 2. 改之前：先看当前列表（记住 id=8 这条的 status）
GET http://localhost:8080/category/page?page=1&pageSize=10
token: {{token}}


### 3. 把 id=8 禁用（status=0）
POST http://localhost:8080/category/status/0?id=8

### 4. 改之后：再看一眼（status 应变 0，updateTime 应更新）
GET http://localhost:8080/category/page?page=1&pageSize=10
token: {{token}}


### 5. 改回来（status=1）
POST http://localhost:8080/category/status/1?id=8
token: {{token}}


### 6. 确认已恢复（status 应变回 1）
GET http://localhost:8080/category/page?page=1&pageSize=10
token: {{token}}
```

三个注意点：

1. **必须先跑第 1 个（登录）**。`> {% client.global.set("token", ...) %}` 是 IDEA 的小脚本：登录成功后自动把 `data.token` 存成变量 `token`，之后 `{{token}}` 会被自动替换。**不先跑登录，`{{token}}` 是空的，后面全 401。**
2. 每个 `###` 是一个**独立小块**，左边小绿箭头可单独运行。按 1→2→3→4→5→6 顺序点。
3. `id=8` 按库里实际数据来。
4. ⚠️ 别忘了：**必须先重启项目**（改过 Controller），否则第 3 步 405。

## 八、第 5 步数据流全景（背下来）

```
前端
  POST /category/status/0?id=8
        │
        ▼
Controller   @PathVariable 拿 status=0，@RequestParam 拿 id=8
        │
        ▼
Service      造一个 Category 对象，只填 4 个字段：
             id=8、status=0、updateTime=现在、updateUser=当前登录员工
        │
        ▼
Mapper       UPDATE category SET status=0, update_time=..., update_user=... WHERE id=8
        │
        ▼
返回影响行数 → Controller 返回 Result.success()
```

> ⚠️ **`updateTime` / `updateUser` 为什么必须手工填？** 因为"公共字段自动填充"（AOP）还没做，那要很后面才学。所以现在只能手动 `setUpdateTime(now())`、`setUpdateUser(BaseContext.getCurrentId())`。

## 九、必记 3 点

1. **`{}` 是占位符，不是字面文字** —— 代码里有花括号，实际 URL 里没有。
2. **路径 vs `?` 的判断标准** —— "要写入的值 / 要操作的对象"放路径；"筛选用"放 `?`。
3. **POST / PUT 别乱用** —— 前后端必须一致，否则 405；跟黑马统一用 POST。

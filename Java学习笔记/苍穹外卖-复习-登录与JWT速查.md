## 🧭 一、主线（一句话串起来）

```
密码不能明文存  →  所以存摘要（MD5）
        ↓
登录 = 把用户输入的密码也变成摘要，两边比一比  →  验身份
        ↓
验过了得让服务器"记住你"，可 HTTP 是无状态的
        ↓
发一张盖了章的通行证（JWT），前端每次带着它  →  认人
```

**四个关键词：摘要 → 比对 → 无状态 → 签发/验签。**

## 🔐 二、第 7 课速查：MD5 密码加密

| 问题 | 答案 |
|---|---|
| 为什么不能存明文？ | 拖库/内鬼/备份泄露一次，用户所有网站的密码一起完蛋（很多人复用密码） |
| MD5 是加密吗？ | **不是**。加密（AES）可逆、有密钥；摘要不可逆、无密钥 |
| MD5 三大特点 | ① 固定长度（32 位十六进制）② 不可逆 ③ 雪崩效应（差一个字全变） |
| 那怎么验密码？ | **再算一遍，比字符串**。永远不要试图"解密"库里的密文 |
| 为什么 MD5 还不够 | 彩虹表：`e10adc3949ba59abbe56e057f20f883e` 一查就是 `123456` |
| 更好的方案 | 加盐 → **BCrypt**（真实项目推荐，自带盐） |
| 用什么工具算 | `DigestUtils.md5DigestAsHex(str.getBytes())` |
| 在哪一层加密 | **Service**，调 Mapper 之前。业务规则不归 Controller/Mapper 管 |
| 改代码就够了吗 | 不够！**历史数据要手动 UPDATE 成密文** |

## 🔑 三、第 8 课速查：登录（验身份）

### 数据流

```
POST /employee/login  {"username":"admin","password":"123456"}
        ↓
Controller   @RequestBody → EmployeeLoginDTO（Spring 帮你 new）
        ↓
Service      ① getByUsername 查人  ② null → 撤
             ③ 明文密码 MD5        ④ 跟库里的比，不一样 → 撤
        ↓
Mapper       SELECT * FROM employee WHERE username = #{username}
        ↓
Controller   Result.success(employee) / Result.error("用户名或密码错误")
```

### 核心代码骨架

```java
// Service
Employee employee = employeeMapper.getByUsername(dto.getUsername());
if (employee == null) return null;

String md5 = DigestUtils.md5DigestAsHex(dto.getPassword().getBytes());
if (!md5.equals(employee.getPassword())) return null;

return employee;

// Controller
Employee employee = employeeService.login(dto);
if (employee == null) return Result.error("用户名或密码错误");
return Result.success(employee);
```

### 三个"为什么"

| 问题 | 答案 |
|---|---|
| 为什么用 DTO 不用 Entity？ | Entity 描述"表里有什么"，DTO 描述"接口要什么"。登录只要 2 个字段，用 Entity 会含糊，还会放过脏字段 |
| 为什么用 WHERE 查？ | 100 个员工还行，10 万个就是全搬进内存。**能在数据库做的筛选，别搬到 Java 里做** |
| 为什么失败提示统一是"用户名或密码错误"？ | 分开提示会让人试出"哪些用户名存在"（**用户名枚举**），下一步就是撞密码 |

### 一句话记住卫语句

```java
if (!md5.equals(...)) return null;    // 错的先撤，主流程平铺到底
```
> 每个 `if` **念一遍中文**：读成"如果密码一样就撤退"就是写反了。

## 🎫 四、第 9 课速查：JWT

| 问题 | 答案 |
|---|---|
| 为什么需要它？ | **HTTP 无状态** —— 每次请求都是"全新见面"，服务器不记得你 |
| Session 的毛病 | 服务器要存（爆内存）、多台服务器不共享、App/跨域别扭 |
| JWT 的结构 | `header.payload.signature`，点号分隔 |
| 哪几段是明文？ | **前两段**！Base64 是编码不是加密，谁都能解开看 |
| 所以能放密码吗？ | **绝对不能**。JWT 保证"改不了"，不保证"看不见" |
| 为什么伪造不了？ | 签名 = `HMAC-SHA256(header.payload, 密钥)`，密钥只在服务器 |
| 服务器怎么验？ | 用密钥把前两段重算一遍签名 → 跟 token 里的比 → 一致 + 没过期 = 认 |
| 所以就不用存东西了？ | 对，**不查库不查内存，密钥一算就知道真假** |
| JWT 的短板 | 注销麻烦（票没到期收不回，真实项目配 Redis 黑名单）、payload 可见、**必须设过期时间** |
| 依赖 | `jjwt-api` + `jjwt-impl` + `jjwt-jackson` **0.12.5**（老教程的 0.9.1 在 JDK 21 上会崩） |

## 🕳️ 五、昨天踩的 3 个新坑

| 坑 | 现象 | 正解 |
|---|---|---|
| **漏写 `!`** | 正确密码登不上，**错密码反而进得去** 😱 | `if (!md5.equals(...)) return null;` |
| `username == null` 检查 | 以为防了 NPE，其实没防住 | 真正会 NPE 的是 `password.getBytes()`（对 null **调方法**才炸；null 当**值**传递没事） |
| 分支没 `return` | 编译报"缺少返回语句" | 方法声明了返回值，**所有路径都要有返回值** |

> 顺带再踩了一次：**同一个 username POST 两次 → 500 `Duplicate entry`**（唯一索引）。

## 📝 六、自测 10 题（先自己答，再看下面答案）

1. 密码为什么不能明文存？MD5 算"加密"吗，为什么？
2. 登录时服务器怎么验证密码？描述一下方向。
3. DTO 和 Entity 有什么区别？为什么登录不用 `Employee` 接参数？
4. 登录的完整链路里，Controller / Service / Mapper 各干了什么？
5. `getByUsername` 为什么用 `WHERE` 查，而不是 `findAll()` 再循环找？
6. 登录代码漏写 `!` 会导致什么后果？为什么编译器查不出来？
7. 登录失败返回 `HTTP 200` + `code:0`，矛盾吗？HTTP 状态码和业务码各管什么？
8. JWT 的三段分别是什么？哪几段是明文？为什么不能放密码？
9. 为什么用 JWT，服务器就不用存 Session 了？
10. 攻击者把 JWT payload 里的 `empId` 从 1 改成 999，为什么不行？

---

<details>
<summary>👉 点开看参考答案</summary>

1. 明文一旦泄露（拖库/备份/内鬼），用户复用密码会连带其它网站遭殃。MD5 **不是加密**：加密可逆、有密钥；摘要不可逆、无密钥。
2. 把**用户输入的明文**加密成摘要，跟**库里的摘要**比字符串。不是把库里的解密出来比。
3. Entity 对应数据库表（10 个字段）；DTO 对应接口入参（2 个字段）。用 Entity 接会让接口参数含糊，还会放过 `status`、`id` 这类脏字段。
4. Controller 收 JSON 并转发；Service 查人 + 加密 + 比对（业务规则）；Mapper 写 SQL 查库。
5. `findAll` 会把全部数据搬进内存，数据量大时纯浪费；`username` 有唯一索引，数据库能秒查。**能在数据库做的筛选别搬到 Java。**
6. 逻辑整个反转：密码正确 → 进 if 返回 null（失败）；密码错误 → 跳过 if 返回 employee（**登录成功**）。编译器只查语法，看不住逻辑，只能靠测试抓（专门测"密码错"这条用例）。
7. 不矛盾。HTTP 状态码说"请求本身送达/走通了吗"（200/404/405/500）；业务码说"这件事办成了吗"（1/0）。前者管路通不通，后者管事办没办成。
8. `header.payload.signature`。**前两段是明文**（Base64 只是编码）。所以不能放密码、身份证 —— JWT 只保证"改不了"，不保证"看不见"。
9. 因为验证不需要查存储：服务器用密钥把 `header.payload` 重算一遍签名，跟 token 里的签名比对，一致且没过期就认。
10. 签名是按**原来的** `header.payload` 算出来的。改了 payload，签名就对不上了；而攻击者没有密钥，**算不出新签名**。

</details>

## 📊 七、自测批改记录（2026-10-06）

**成绩：2 对 ✅ / 3 半对 ⚠️ / 5 不会 ❌**

| 题 | 结果 | 批注 |
|---|---|---|
| 1 MD5 是不是加密 | ✅ 对 | "不能解开"抓到了要害：**不可逆 = 摘要**，加密是可逆的 |
| 2 验证密码的方向 | ⚠️ 背下了流程，没答"方向" | 方向＝**拿用户输入的明文去算摘要**，不是把库里的密文"变回去" |
| 3 DTO vs Entity | ⚠️ 感觉对了，说法含糊 | 标准说法：Entity 描述"**表里有什么**"，DTO 描述"**接口要什么**" |
| 4 三层各干什么 | ⚠️ **Mapper 的职责说错了** | Mapper **只负责"按条件把人取出来"，不做对比**！对比是 Service 的活 |
| 5 为什么用 WHERE | ✅ 对 | 补充：还省掉了"把所有数据搬进内存" |
| 6 漏写 `!` | ❌ | 逻辑整个反转：正确密码登不上、错密码反而进得去 |
| 7 HTTP 200 + code 0 | ❌ | 一个管"信送到没有"，一个管"事办成没有" |
| 8 JWT 三段 | ❌ | header.payload.signature，**前两段明文** |
| 9 为什么不用存 Session | ❌ | 验签靠密钥计算，不需要查任何存储 |
| 10 改了 payload 为什么不行 | ❌ | 签名是按原内容算的，改了就对不上；没密钥刻不出新章 |

### 需要补的三处（重点）

**① Mapper 不做对比，只做"取数"**

```
Controller  前台接待   —— 收请求、转达，不做业务判断
Service     办事员     —— 动脑子：查人 → 加密 → 比对 → 决定放不放行
Mapper      档案管理员 —— 只按条子取档案，一个字都不判断
```

> `SELECT * FROM employee WHERE username = ?` 是"把这个人取出来"，
> **"取出来之后密码对不对"是 Service 的判断**。职责不能串。

**② 验证密码的"方向"**

```
✅ 正确方向
   用户输入 "123456"  →（算 MD5）→  e10adc39...  →（字符串比对）→  库里的 e10adc39...

❌ 错误方向（做不到，也不需要）
   库里的 e10adc39...  →（解密）→  "123456"
```

**③ JWT 三题一句话版（记忆锚点）**

| 问题 | 一句话答案 |
|---|---|
| 三段是什么 | **头、内容、印章** = `header.payload.signature`；头和内容**明文** |
| 为什么不用存 Session | 验证 = **用密钥重算一遍印章**，算对就认，不用查库查内存 |
| 改 payload 为什么不行 | 内容改了，**印章就对不上**；没有密钥，**刻不出新章** |

> 🎯 **一个比喻打包记住**：
> Session = 给你一个**储物柜号码牌**，东西存在服务器的柜子里（柜子爆了、换一家店就取不到）。
> JWT = 给你一张**盖了章的通行证**，你自己揣着，服务器**只认章，不认人**。
